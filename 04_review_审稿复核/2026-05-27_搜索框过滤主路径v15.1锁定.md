### 代码核心（SearchFilter.java setAdapter callback 内）

```java
// 1) 找到 declares getView 的类（q2 沿继承链 → f0）
Class<?> gvCls = null;
for (Class<?> c = adapter.getClass();
     c != null && c != Object.class
             && c != android.widget.BaseAdapter.class;
     c = c.getSuperclass()) {
    boolean has = false;
    for (Method m : c.getDeclaredMethods()) {
        if ("getView".equals(m.getName())) { has = true; break; }
    }
    if (has) { gvCls = c; break; }
}
// gvCls = com.tencent.mm.plugin.fts.ui.f0

// 2) afterHook 拿 getResult() 即 row View，调 getItem(pos) 抽 wxid
XposedBridge.hookAllMethods(gvCls, "getView", new XC_MethodHook() {
    @Override
    protected void afterHookedMethod(MethodHookParam p) {
        int pos = (Integer) p.args[0];
        View v = (View) p.getResult();

        if (!StateMachine.getInstance().isActive()) { restoreView(v); return; }
        Set<String> hidden = Bridge.getInstance().allHiddenIds();
        if (hidden.isEmpty()) { restoreView(v); return; }

        Object item = adapter.getItem(pos);  // tz2.u1 / tz2.s1 / tz2.g0
        String id = extractAnyWxid(item);    // tz2.u1.f.s = wxid
        if (id == null || !hidden.contains(id)) { restoreView(v); return; }

        v.setVisibility(View.GONE);
        lp.height = 0;
        mlp.topMargin = 0; mlp.bottomMargin = 0;  // 抹除 row gap
    }
});

// 3) 清掉 ListView divider 让 GONE row 视觉无残留
lv.setDivider(null);
lv.setDividerHeight(0);
```

### 关键设计点

| 点 | 解释 |
|----|------|
| **afterHook 而不是 beforeHook** | beforeHook 时 View 还未 bind，afterHook 拿到的 `p.getResult()` 已是 ready 的 row View |
| **不改 args[0]、不 setResult** | 让 WeChat 渲染流自然跑完，我们只在结尾"染色"（GONE）。5-hook offset 路线的失败教训 |
| **沿继承链找 declares getView** | q2 不 declare getView，f0 declare。`hookAllMethods(q2.class, "getView")` 匹配 0 个静默失败，必须爬到 f0 |
| **margin=0 + setDivider(null)** | GONE row 高度 0 后，ListView 的 row margin 和 divider 仍残留几像素。两刀齐下消除 |

## 三、新增 3 条铁律

### F-32x：ss4.p.onBindViewHolder 永久废弃

**现象**：ss4.p 是 FTSMainUI 的 RecyclerView adapter，本体 `vis=0`，看似可见。

**真相**：ss4.p 的父级 ConstraintLayout `vis=8 (GONE)`，整个子树都不上屏。真渲染容器是同层 ListView（被 HeaderViewListAdapter 包着 q2）。

**证据**：`bug排查/fts_tree_v2.log` L243（父级 GONE）/ L273（ListView vis=0 count=5）。

**铁律**：判断 view 是否上屏不能只看自身 visibility，必须沿父链查。

### F-32y：q2.j(View, jz2.g, boolean) 主路径废弃

**现象**：v10 装机看到 `[SF:gv] blocked` 时误以为 q2.j 是主路径，实际是 q2.getView 拦下来的。q2.j hook 装上 0 触发。

**真相**：8.0.71 的 q2 adapter 渲染搜索结果**不调用 q2.j 方法**，而是继承 f0 的 getView 直接绑定 row。q2.j 留作 backstop 无害但不主导。

**证据**：final_v15 装机日志 `[SF:q2] data item dump` 0 次出现，`[SF:gv] blocked` 14 次。

**铁律**：声明方法 ≠ 被调用方法。装 hook 后必须看运行时实际命中数。

### F-32z：SearchFilter 5-hook offset 永久废弃

**现象**：试图通过 hook getCount setResult(orig-skip) + getView/getItem 翻译 args[0] 实现"密友 row 不存在"。装机后搜索结果区**完全空白** + ANR。

**真相**：q2 内部有独立的 data swap 机制（搜索词变化时换 backing list）。我们 setResult 让 ListView 看到的 count 与 q2 内部 list size 不匹配，ListView 进入混乱渲染态或不渲染。

**证据**：final_v11/v12/v13/v14 装机连续 4 次空白，关 5-hook offset 后立即恢复。

**铁律**：BaseAdapter 的 getCount 是 WeChat 内部状态机的一部分，不能动 setResult。如要消密友 row 视觉残留，用 `setDivider(null)` + `lp.height=0` + `margin=0` 在 view 层做。
