## 3. 决定性问题答案：握手校验什么身份？

### 结论（L2）

**迁移接收端在 Java 层不校验 APK 包名，也不校验 APK 签名（`getPackageInfo` / `GET_SIGNATURES` / `GET_SIGNING_CERTIFICATES` / `SigningInfo` 均无调用）。**

对 `dm1/`、`am1/`、`ql1/`、`rl1/`、`pl1/`、`xl1/`、`com.tencent.mm.lan_cs/`、`com.tencent.wechat.aff.migration/`、`com.tencent.mm.plugin.backup/` 全量关键词扫描，**零命中**（L2 负向证据）。

实际校验的是 **协议内身份 + 微信账号身份 + 局域网可达性**，分两条栈：

## 5. 裁决：hook 伪装官方身份能否骗过迁移？

### 一句话

**不能指望靠 hook `getPackageName` / `getPackageInfo` / `GET_SIGNATURES` 骗过迁移——Java 层迁移代码根本不读这些 API；真正卡点在微信账号绑定、协议 authKey/hello-ok、局域网同网段，以及可能的 aff 原生层逻辑。**

### 分项裁决

| 手段 | 能否骗过 | 依据 |
|---|---|---|
| hook 包名 → `com.tencent.mm` | **无效（L2）** | 迁移相关 Java 包零 PM 调用 |
| hook 签名 → 官方证书 | **无效（L2）** | 同上；握手用 `"key"` + deviceId + hello/ok，与 APK 签名无关 |
| 共存改包名版作接收端 | **有条件可能（L3）** | 身份绑定到**微信账号**（sha256 wxid）+ 服务器 CGI，非 APK 身份；前提是修改版能登录同一账号、能进迁移 UI、服务器不拒 |
| 真正难点 | **账号 / 服务器 / 原生（L2+L4）** | `migratemsggetbindinfo` 需有效登录态；`iam_feat_roam` native 未审；经典栈还要求同 WiFi 同网段 |

### 改包共存版实操含义

1. **迁移不认「是不是官方 APK」**，认的是「是不是同一个微信账号 + 正确 QR/握手密钥 + 网络可达」。
2. 若修改版**登录/进迁移页/调 CGI 正常**，接收迁移的 Java 层**没有**额外包名墙。
3. hook 伪装官方身份是**走错方向**；应排查：
   - 修改版能否完成 `migratemsggetbindinfo`（服务器是否按 UA/设备指纹拒）
   - `bleAuthKey` / QR 时效
   - 经典栈 WiFi 网段匹配（`e.java:699-726`）
   - aff native 是否有 jadx 不可见的完整性校验（**需 Frida L1**）
