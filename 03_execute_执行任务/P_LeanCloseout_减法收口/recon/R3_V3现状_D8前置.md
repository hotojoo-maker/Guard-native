## 1. ① `gen_registry_cipher.py` 的 `--recipe` / per-release 机制现状【L2】

### 1.1 key 派生 = 三轴折叠

`derive_registry_key()`（`tools/gen_registry_cipher.py:80-100`，须与 `config_crypto.cpp` 逐字节同源）把 AES-128 key 由三段折出：

| 轴 | 料 | 来源 | 是否 per-release |
|---|---|---|:---:|
| 静态散段 | `_SEG_A/B/C` | 脚本 + SO 双写常量 | 否（固定） |
| **cert 轴** | `_CERT_SHA256` | **脚本内硬编码常量** `ca421ec3…`（`:65-70`） | **否（硬编码）** |
| **server seed 轴** | `s_rel`（32B） | `--recipe` 读 `release/secrets/<id>.json` | **是（recipe 驱动）** |

### 1.2 `--recipe` 做什么 / 不做什么

- **做**：`--recipe` → `_apply_recipe()`（`:141-161`）从 per-release JSON 读 **`registry_mode`** + **`s_rel_b64`**，作为与 miyou-server 共享的**唯一真相**（`RELEASE_RECIPE契约.md`）。`prod_server_lock` 无 `s_rel` 直接 `SystemExit`。`s_rel` 折进密文、**不进客户端二进制**。
- **不做**：recipe **没有 cert 字段**。`release_recipe.example.json` 字段 = `release_id/schema_id/wechat_version/kid/registry_mode/s_rel_b64/wrap_key_b64/ed25519_public_b64/endpoints/funnel_url` —— **无证书**。契约 §2 字段表同样无 cert。【L2】
- 结论：**`--recipe` 只承载「server seed 轴」的 per-release；「cert 轴」完全在 recipe 之外，靠手改脚本常量 + `keytool` 重算（docstring `:17-22`）。**

### 1.3 现网状态

- `android_8071` 已切 `prod_server_lock`，`registry_cipher.inc` 产物 `GUARD_REGISTRY_REQUIRES_SERVER_SEED=1`，文档记 2026-06-11 线上 unwrap 后 `recipeOk=true`（`PROTECTION_MAP §10.6` / `RELEASE_RECIPE契约 §5`）。【L2 文档；原始 L1 日志本次未复核】

## 2. ② 官替/共存「每发行证书重生 cipher」接到哪 + `EXPECTED_CERT`/`_CERT_SHA256` 是否随发行线

### 2.1 cert 轴：两处硬编码、同源、**不随 recipe / 不随 flavor**【L2】

| 位置 | 值 | 形态 | 随发行线？ |
|---|---|---|:---:|
| `gen_registry_cipher.py:65-70` `_CERT_SHA256` | `ca421ec3…` | 脚本硬编码 | 否，手改 |
| `CompatProbe.java:33-37` `EXPECTED_CERT` | `ca421ec3…`（同值） | Java 硬编码 | 否，手改 |
| 发版官 skill「不可变」表 / `§10.9` 注3 | `ca421ec3…` | 「按包档案改这里」 | **手动**，非自动 |

→ **「每发行证书重生 cipher」目前没有自动接入点**；它是「发版时按包档案**手改两处常量** + 重跑 gen + 重编 SO」的人肉流程，不是 recipe/flavor 驱动的流水线。【L2】

### 2.2 运行时证书**源**：仍读模块 APK 自身签名（V3 切换未做）【L2】

- `ModuleMain.initZygote` 存 `sModulePath`（`:55`）；`bindSigningCert()`（`:280-314`）+ `CompatProbe.checkSignature()`（`CompatProbe.java:71-90`）都用 `getPackageArchiveInfo(sModulePath, …)` 读**模块自身 APK** 证书 → `setBindingMaterial(sha)`。
- D-016 §影响 ① + `§10.6 ⚠️①` 明确：V3 落地要把证书源从 `sModulePath` 改读**宿主自身签名**（`getPackageInfo(getPackageName(), GET_SIGNING_CERTIFICATES)`）+ 同步改 `_CERT_SHA256`。**此切换尚未实现。**【L2】

### 2.3 flavor 注入现状：只注包名，未注 release_id / cert【L2】

- `build.gradle:47-66`：`official`(com.tencent.mm) / `coexist`(com.tencent.mn) **只**注 `GUARD_WX_PKG`（`buildConfigField` + cmake `-DGUARD_WX_PKG`）。
- `build.gradle:75-98`：两 flavor **同一 `guardFixed` keystore** 签名（对齐 D-017）。
- **drift（实锤）**：`AppConfig.java:50` `GUARD_RELEASE_ID = "android_8071"` **硬编码、非 flavor 注入**。服务器已建 `android_8071_coexist` 线，但**共存客户端仍上报 `android_8071`**（`S3a0/result.md:126/144/189`、`RELEASE_RULES:219-221`）。→ **共存版未真正走自己的发行线**，s_rel/registry 与官替共用、s_rel 轮换会连坐官替。【L2】

### 2.4 共存包名误判（`§10.6 ⚠️③`）：疑已大体解决【L2/L3】

- `anti_tamper.cpp:43-47`：`tamper_check` 比对 `EXPECTED_PACKAGE`；该常量由 `GUARD_WX_PKG` 派生（cmake 注入）。`RELEASE_RULES:218` 记「Java 宿主包白名单已随 `BuildConfig.GUARD_WX_PKG` 区分」；`S3a0/result.md:99/158` 记两包 SO 哈希不同正因 `GUARD_EXPECTED_PACKAGE` 不同（mm vs mn）。→ 共存版包名误判风险**应已随包名注入闭合**，但**未见共存版「无 `PACKAGE_MISMATCH`」装机 L1 收据**，留 L4 待验。

## 4. ❓ 需指挥裁决：D-017 与「每发行证书」措辞张力

- **D-016/§10.6（06-08~11）** 写法：V3 要「每发行**证书**重生 cipher」+ 切证书源（默认不同包/不同证书的语境）。
- **D-017（06-23，最新）** 裁定：官替/共存**同一固定 keystore**（`ca421ec3`），微信靠**包名**区分、后台靠**版本字段**区分；签名轴恒定。
- **张力**：若 keystore 永久固定，则「每发行证书」恒为同一值，cert 轴**不需要** per-release 重生；真正 per-release 的变量只剩 `s_rel`（recipe 已驱动）。那么任务卡 §4 D8 的「每发行证书重生 cipher」是否应改读作「**每发行线**换 `s_rel` 重生 cipher + V3 证书源对齐一次到位」？
- **影响**：若按 D-017 解读，G2「cert 轴 per-release 流水线」可降级为「一次性对齐 + 固定」，D8 前置据此**收窄**；若按字面坚持 per-cert，则需补 cert 入 recipe 的机制。**此处不替指挥定调（G1 不猜），标 ❓ 待裁。**
