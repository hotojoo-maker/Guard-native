## 3. 重点 6 问

### 1. SSAID 算法：输入是什么，是否逐机派生，本机官方值是什么？

**答案：**

- 输入：`user_key` + `BE32(len(sigDER)) || sigDER`。
- 算法：`HMAC-SHA256(user_key, BE32(len(sigDER)) || sigDER)[:8] -> 16 hex`。
- `user_key`：每台机随机，存 `/data/system/users/0/settings_ssaid.xml`，root 才能读。
- 是否逐机派生：**是**。同签名在不同设备不同；同设备同签名相同；同设备不同签名不同。
- 本机官方 SSAID：`05f894e8e1e260fa`（官方 DER 计算命中）。
- 共存包实测 SSAID：`3bd03c4c6311c6d8`（旧 debug key 持久值）或 testkey 相关值，核心结论是不等于官方。

**对应设计：**

- A2：签名喂官方时，`android_id` 必须同时喂“官方签名在本机派生出的 SSAID”，否则签名与 android_id 不自洽。
- E9：`W_dev` 的设备材料必须来自真设备材料，不能读到 A2 喂给官方包的 SSAID；因此必须走 `rawAndroidId` memoize 预热。

### 2. A2 签名轴：c$p 是否走 Java getPackageInfo？Java hook 能否覆盖？

**答案：**

- 已定为 **(b) 经 Java**，不是 native 独读。
- L1 证据：`c$p.aa` 调 `getPackageInfo(GET_SIGNATURES)` + `Signature.toByteArray()`；`Signature.toByteArray` 栈里直接出现 `com.tencent.mm.normsg.c$p.aa`。
- L4 主动实证：喂官方 DER 后，`c$p.ad` 读到 `18c867f0` / len 751；对照无 spoof 为 `e89b158e`。

**对应设计：**

- `getPackageInfo(self, GET_SIGNATURES | GET_SIGNING_CERTIFICATES)` afterHook 是 A2 签名轴主闸。
- 不要直接 hook `Signature.toByteArray()` 全局替换，避免误伤他包签名读取。
- A2 只喂自身官方值，`c$p` 查 `bin.mt.plus` 等他包时不要改。

### 3. 包名轴：哪些 caller 读包名？是否只需选择性喂，禁全局 hook？

**答案：**

关键读点：

- `c$p.aa <- WCProbe.e/f <- normsg.u`：`getPackageInfo(self)`，检测咽喉。
- `bu5.a`：`getPackageInfo(self)`，Flutter 上报/插件路径。
- LiteApp / Cronet / XWeb / 定位 SDK 等也会读自身包名或 UA。
- `Context.getPackageName()` 实捕 363 个调用方，遍布业务、文件路径、authority、SDK。
- native `/proc/self/cmdline` 冷启动补验为 0 读（覆盖主要目标 SO，仍以真号 L4 终验兜底）。

**结论：**

- 只能选择性喂：`getPackageInfo` / `getApplicationInfo` 在 `normsg/bu5` caller 下喂官方包名和路径。
- **禁止全局 hook `getPackageName()`**，否则数据目录、provider authority、业务路径会错，大概率崩。

### 4. 检测面 + 上报链：启动期读了哪些，打包成什么，哪些是我方包差异？

**客户端采集事实：**

- 环境 / 完整性：`ro.boot.verifiedbootstate`、`vbmeta.device_state`、`veritymode`、`flash.locked`、`ro.secure`、`ro.debuggable`、`sys.oem_unlock_allowed`、build fingerprint 等。
- 设备指纹：model / brand / board / hardware / release / cpu abi 等。
- 身份：签名 MD5、包名、sourceDir、数据路径、android_id。
- 环境画像：他包枚举（含 root/RE 工具）、无障碍服务、输入法、logcat 快照、maps/smaps。
- 扩面候选：GPU/GL、getauxval、dladdr、realpath、sigaction 等（L2，部分未 L1）。

**上报链事实：**

```text
采集明文 -> c$p / WCProbe$Info.f -> protobuf 信封
field8 时间戳 / field1 版本 / field2=2 / field3 高熵密文
-> u.uc / NormsgDataService -> 网络
```

**我方/共存包差异：**

- 签名 MD5 非官方：官方 `18c867f0` vs 共存 testkey `e89b158e`。
- android_id 非官方签名派生值，与官方 SSAID 不同。
- 包名 / 路径可能非官方；但检测咽喉目前可通过 Java `getPackageInfo` 选择性喂官方。
- root/解锁/环境在官方包同机也会被读到，且官方包满脏环境长期未被判异常；因此不作为客户端硬闸。

**边界：**

只能写“客户端采集并上报这些输入”；没有服务器侧石锤时，不写服务器如何判。

### 5. 热更新：官方包是否可不改版本号热更新，影响检测面？

**已证：**

- `libcso.so`：native SO 热补丁容器，8.0.71 与 8.0.68 字节级相同；本体无网络符号，不自己下载，负责应用 patch。
- Tinker：DEX/SO 补丁层，8.0.71 Java 链路完整，支持不发版加载 patch。
- Java 层有低风险候选可阻断新热更新：libcso C1/C2，Tinker C1+C3+C4/C5。

**未证：**

- 没有 L1 证明 8.0.71 已经通过 libcso/Tinker 推过“新检测规则”。
- 所以“热更新会漂移检测面”目前是机制 L2 + 风险 L3，不是 L1 结论。

**对应设计：**

- 热更新冻结可作为预防性方案；
- 落地前必须做 8.0.71 动态重验；
- 不应把“没冻结就一定被新检测打”写成结论。

### 6. 漂移检查：研究线与 DESIGN.md 是否冲突？

**已对齐 / 支撑：**

- DESIGN §0 “核心咽喉 = `getPackageInfo` / `c$p`，喂官方值 + 借官方眼睛”被 A2 证据支撑。
- DESIGN “root/env 不作为硬闸，客户端不读 `ro.boot.*`”被权威账 §0 支撑。
- DESIGN “A2 三轴 = 签名 / android_id / 包名路径”被 §十四、§十六支撑。
- E9 “设备材料必须与 A2 android_id 同源隔离”被 SSAID 证据和 R4b 支撑。

**需要纠偏 / 防误读：**

1. 旧索引曾写“包名 = 共存固有命门 / 必须官替”，已被 2026-06-21 `PKGNAME_READERS` 更新为：检测链冷启 cmdline 0 读，c$p Java 咽喉可选择性喂，**不因包名轴强制官替**。
2. 环境轴可被官方包读取，但研究线 §0 裁定它不是当前硬根；不要把动态明文环境采集误读成“必须做 root/env spoof”。
3. 热更新通道机制存在，但“下发新检测”无 L1；不能把预防性冻结写成已经发生的攻击面。
4. 三方跳转属于跨进程 gate A，不是 A2 进程内三轴能解决；不要把“官替/共存防封”与“三方登录/支付”混为一个目标。
5. E9 设计中的 `D_mat` 不能使用 A2 喂官方后的 android_id；否则 W_dev 全机同值，牙③自废。

## 4. 大白话总览

研究线现在已经把“官方包到底看什么”摸得比较清楚了：

- **它会看很多环境**：root、解锁、系统属性、设备指纹、他包、无障碍、输入法、maps/smaps、热更新状态等。
- **但真正硬区别是身份**：签名、android_id、包名/路径。尤其签名是唯一硬键。
- **签名和包名这条路都过 Java 咽喉**：`getPackageInfo` 是最关键的闸口，`c$p` 没有绕开 Java 自己独读签名。
- **android_id 不是随机常量**：它由本机 user_key + 签名 DER 派生，所以非官方签名会自然带出不同 SSAID。
- **上报链确实存在**：采集明文进 `c$p`，打成 protobuf 信封，field3 加密后上送；我们能证明“采集/上报输入”，但不能猜服务器判分。

因此 DESIGN 的核心打法是被证据支撑的：

```text
不自己造环境检测
不读 ro.boot.*
卡官方查身份的咽喉 getPackageInfo / c$p
给官方包灌官方签名 / SSAID / 包名路径
同时借这个咽喉观察签名是否被换、包是否被改
异常时不给 A2 真料 / registry 真料，只散沙
```

对 E9 来说，研究线最关键的价值是证明：**设备材料必须和 A2 android_id 轴隔离**。A2 是给官方包看的“官方 SSAID”，E9 是给我方服务器/registry 钥匙用的“真设备材料”。这两个如果混了，W_dev 就从“一机一密”变成“全机同值”，等于把最重要的一颗牙拔掉。

## 6. 最关键 3 条发现

1. **A2 的根证据是硬的**：`c$p` 经 Java `getPackageInfo + Signature.toByteArray` 读签名，喂官方 DER 后 `c$p` 实读官方 `18c867f0`；A2 签名轴成立。
2. **A2 必须三轴联动**：签名喂官方后，android_id 也必须喂官方签名对应 SSAID，包名/路径只在检测咽喉选择性喂；全局 `getPackageName` 禁止。
3. **E9 必须与 A2 同盘隔离**：W_dev 用真设备材料，A2 用官方 SSAID；两者都碰 ANDROID_ID，必须 `rawAndroidId` memoize 预热，否则设备绑定和 W_dev 一起塌。
