## 1. 破防判定总标准（S3b · 写死）

能反编译、能抽模块、能看到 `NativeBridge`、能 hook `nativeIsAuthorized()` —— **都不算破防**（预期威胁）。

**真正破防只有一个标准**：

```
无合法 envelope / 无 S_rel / 无有效签名时，
仍能让 GuardRuntime.getRecipe() 返回真实 registry recipe，且业务 hook 正常命中。
```

一切结论围绕 `recipeOk` / `registrySummary != scatter` / `isConfigReady()` / 关键 gateway `getRecipe()` 展开。

## 3. 静态分析任务书（给外部 AI · deepseek / claude code）

目标：用「白盒静态」找三条破防路线，验证 §1 标准。**只读，不改码。**

### A. 明文泄漏面（release 包内能否直接搜到核心 hook）

- 反编译 release APK，搜核心混淆名 / 字段：`MvvmList`、`fc5.g`、`z3`、`kc5.v0`、`LikeUserList`、`CommentUserList`、`na4.b`、`la4.p`。
- 判定：release `RegistryFallback` 应全 `""`（fail-closed）；若仍有 5 处内联明文（`ContactDiscoveryHook`/`ContactLabelHideGuard`/`MomentsFilter`）即 C5b/D8 旧账暴露面。
- 产出：明文清单 + 文件:行 + 是否兜底层已空。

### B. NOP / hook 绕过（能否假授权拿真配方）

- 找并尝试绕：`NativeBridge.nativeIsAuthorized()` / `nativeGetAuthState()` / `StateMachine.isVipAuthorized()` / UI 授权显示。
- 判定（关键）：即使全 NOP 成 true，只要无合法 envelope，`GuardRuntime.getRecipe()` 仍应散沙（真锁在「服务器种子解 registry」，不在客户端布尔）。能让 getRecipe 出真 registry = 真破防。

### C. 自建服务器 / 替换公钥（能否伪造 envelope）

- 尝试：替换客户端内置 Ed25519 公钥 + 自建服务器发自签 envelope。
- 判定：客户端 `AuthEnvelopeVerifier` 用内置公钥验签，私钥只在服务端；伪造签名应验签失败 → 散沙。能解出真 registry = 真破防。
- 附：牙③ W_dev（一机一密）+ 牙④（expire floor）状态见 `P_RB1/钥匙加固_KeyHardening设计.md`；服务器 KDF 镜像自测 `I:\miyou-server\guard_selftest.py`。

### 服务器侧可打的 live 面（需测试卡）

- `POST /api/v1/guard/envelope` 带异常 `client.cert`/`client.schema`/探针键 → 看 `q` 升到 `>=3`、`k` 变诱饵（蜜罐：仍 200 出 envelope，但客户端散沙）。风险阈值：`GUARD_RISK_SUSPICIOUS=70`→q2、`GUARD_RISK_HONEY=110`→q3。
- 后台「紧急停用」某 release 后再打 envelope → **当前预期仍能出 envelope**（G4 缺口，见 T11）。
